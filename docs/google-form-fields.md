# 表單欄位對照表：\*體重維持紀錄

`tools/create-google-form.gs` 的 `itemSpecs()` 是**唯一的欄位定義來源**。
本檔是給人看的對照表，改欄位時兩邊都要更新。

## 欄位與回覆試算表欄位對應

表單題目順序＝回覆試算表欄位順序。A 欄是時間戳記，故第 n 題落在第 n+1 欄。

| 欄 | 題目 | 型態 | 選項 |
|---|---|---|---|
| A | 時間戳記 | 自動 | — |
| B | 姓名 | 簡答 | — |
| C | 西元出生年 | 簡答 | — |
| （末欄） | 回診日期 | 日期 | 後來加的，故落在最後一欄；見末節 |
| D | 體重(kg) | 簡答 | — |
| E | 身高(cm) | 簡答 | — |
| F | BMI分級 | 單選 | 小於24但腰圍超標／24-27／27-30／30-35／大於35 |
| G | 腰圍(cm) | 簡答 | —（可留空） |
| H | 與前次相比體重變化 | 單選 | 下降／無變化／上升 |
| I | 飲食習慣 | 複選 | 外食居多／含糖飲料／偏好肉類／偏好飯、麵食類／甜點、餅乾類／宵夜／經常飲酒／其他 |
| J | 運動頻率 | 單選 | 無／有 |
| K | 每週運動頻率 | 單選 | 1-3次／3-5次／每天／假日／**無** |
| L | 每次運動時間 | 單選 | 30分鐘以內／30至60分鐘／60分鐘以上／**無** |
| M | 運動類型 | 複選 | 走路／快走／慢跑／重訓／瑜珈／球類／腳踏車／游泳／核心訓練／其他／**無** |
| N | 目前用藥 | 單選 | 無用藥／生活型態、Mounjaro、Ozempic、Wegovy、Saxenda、Rybelsus、Contrave、Xenical、Jardiance、Acarbose、併用／轉換兩種 |
| O | 藥物劑量 | 簡答 | 由工具端下拉產生固定格式字串 |

K／L／M 的「無」選項是為了避免表單分支：運動頻率選「無」時，工具自動把這三題填「無」。

## 藥物劑量的設計

劑量隨藥而異。若表單為 11 種藥各做一題劑量下拉，就得分頁分支 → 又踩回 `pageHistory`。
故表單只放一題簡答，**由 `index.html` 的 `DOSE_OPTIONS` 依所選藥物動態切換下拉**，
送出時組成 `藥名 + 空格 + 劑量`：

| 藥 | 劑量選項 |
|---|---|
| 無用藥／生活型態 | 無 |
| Mounjaro | 2.5／5／7.5／10／12.5／15 mg/週 |
| Ozempic | 0.25／0.5／1.0 mg/週 |
| Wegovy | 0.25／0.5／1.0／1.7／2.4 mg/週 |
| Saxenda | 0.6／1.2／1.8／2.4／3.0 mg/日 |
| Rybelsus | 3／7／14 mg/日 |
| Contrave | 1～4 錠/日 |
| Xenical | 120 mg qd／bid／tid |
| Jardiance | 10／25 mg/日 |
| Acarbose | 50／100 mg tid |
| 併用／轉換兩種 | **自由文字**（無法列舉，例：`Ozempic 1.0 mg/週 轉 Mounjaro 5 mg/週`） |

送出範例：`Mounjaro 7.5 mg/週`、`無用藥／生活型態 無`。

## 建表步驟

1. <https://script.google.com> → 新增專案 → 貼上 `tools/create-google-form.gs` 全部內容
2. 函式選 `buildAll` → 執行 → 授權（Forms／Sheets／Drive）
3. 看「執行紀錄」（Ctrl+Enter），把印出的 `FORM_ID` 與 `ENTRY` 兩段貼進 `index.html`
4. 確認表單與試算表已進「門診工具-正式運作中」；若搬移失敗會在紀錄裡提示，手動拖即可

## 回覆試算表的三個分頁

| 分頁 | 內容 |
|---|---|
| 表單回應 1 | 原始逐筆回覆 |
| 個案歷程 | 黃格填姓名＋出生年 → 該人每次回診的體重、腰圍、用藥劑量、與前次差、與首次差、累積減重%，附體重折線圖 |
| 個案總表 | 每人一列：回診次數、首次／最新日期與體重、總變化、累積減重% |

## 改欄位時的注意事項

- **改動題目順序或新增題目後，一定要重跑 `repair()`**（或 `reorderFields()`）重建兩張
  分析分頁。公式的欄位位置是執行當下由 `colMap()` 讀表頭解析出來的，不會自己跟著變。
- 題目**標題文字就是欄位的識別碼**，改標題等於改識別碼。若要改標題，
  `colMap()` 的查詢鍵（`buildHistorySheet`／`buildSummarySheet` 裡的 `need(C, '...')`）
  也要一起改，否則會直接丟出「找不到欄位」的錯誤——這是刻意的，寧可報錯也不要靜默算錯。
- **選項字串一字不差**，尤其全形斜線 `／`。對不上 Google 會靜默丟棄那一題。
- 表單端一律不設必填，必填改在 `index.html` 的 `validate()`。

## 為什麼下拉裡沒有「手術」

官方 `normalizeDrug()` 有「手術」分類（`bariatric`／`GS`／`ESG`／`外科`／代碼 `7`），
2026_07 資料庫共 14 筆。**但手術個案在減重門診不需追蹤**（2026-08-18 使用者指示），
不屬於維持期回診工具的服務對象，故用藥下拉刻意不列這個選項。

曾經加過又撤掉，不要再加回來。

## 欄位定位方式（2026-08-18 改）

公式**不寫死欄位字母**，改由 `colMap()` 讀回應分頁第一列的表頭，解析出
`{題目: 欄號}` 再組公式。原因：把身高調到體重之前時，回應分頁的欄位可能跟著換位，
寫死字母會讓 `個案歷程`／`個案總表` 整排錯位，而且是靜默算錯、不會報錯。

已用 dry-run 驗證兩種情境都產生正確公式：欄位維持原順序（體重在 D）、
以及欄位跟著表單換位（體重移到 E），體重的參照都會自動跟上。

找不到欄位時 `need()` 會丟出明確錯誤並列出目前表頭，不會讓公式指到錯的欄。

## 實測：調整表單題目順序不會連動試算表欄位

2026-08-18 用 `reorderFields()` 把「身高(cm)」從第 4 題移到第 3 題，執行紀錄顯示：

- 表單題目變成：姓名 → 西元出生年 → **身高(cm)** → **體重(kg)** → BMI分級 → …
- 回應分頁欄位**維持不變**：A=Timestamp、B=姓名、C=西元出生年、**D=體重(kg)**、
  **E=身高(cm)**、F=BMI分級 → …

**結論：試算表欄位順序在分頁建立當下就固定了，之後調整表單題目順序不會移動既有欄位。**
（新增題目則是往後追加成新欄。）

所以表單上看到的順序和試算表欄位順序**本來就會不一致**，這是正常的，不要「順手修正」。
公式用 `colMap()` 讀表頭解析，兩種情況都正確——這也是不寫死欄位字母的價值：
若當初照表單的新順序把公式手動改成 D=身高，反而會全部錯掉。

## 「回診日期」欄（2026-08-18 加）

Google 表單只記錄**送出時間**。補過去的回診紀錄時全部都是同一天送出，
歷程會擠成同一天的一堆點，排序、與前次差、折線圖全部失去意義——而且不會報錯。

故加一題「回診日期」（日期型），並讓兩張分析分頁改用它：

```
IF(回診日期欄="", Timestamp欄, 回診日期欄)
```

空白才退回送出時間，所以早期沒填日期的紀錄也不會壞。

**`個案總表` 因此不能用 QUERY 的 min/max 取首次／最新日期**（QUERY 無法在欄位上套 IF），
改用 `SORT + INDEX` 的陣列公式，與首次／最新體重同一套寫法。

### 日期題的送出參數（實測結果）

**日期題是單一參數，值為 `YYYY-MM-DD`**：

```
entry.1485371335=2026-03-14
```

網路上常見的說法是日期題要拆成 `entry.N_year` / `_month` / `_day` 三個參數——
**這份表單實測不是**（2026-08-18 由 `addVisitDateField()` 印出預填網址確認）。
所以才要讓程式印出來，不要照抄別人的格式。

工具端直接送 `YYYY-MM-DD` 字串，不經過 `Date` 物件，避免時區換算把日期偏移一天。

> 附帶觀察：Apps Script 裡用 `new Date(2026, 7, 18)` 產生的預填網址是 `2026-08-17`，
> 差一天。那是 Apps Script 專案時區與表單呈現的落差，不影響工具（工具送字串）。
> 但若日後要在 Apps Script 裡程式化寫入日期，記得先確認專案時區。

### 防呆

`ENTRY.visitDate` 還沒填好之前，工具**只允許送出「今天」的紀錄**；選了其他日期會被擋下
並說明原因。否則補舊資料會被記成送出當天，且整條歷程靜默算錯。
（2026-08-18 已填入 `entry.1485371335`，此防呆現為備援，正常不會觸發。）

## 分頁分不出「沒資料」與「公式壞了」時的處理

兩張分析分頁的公式一律用 **`IFNA`**，不要用 `IFERROR`：

- `IFNA` 只吞 `#N/A`（FILTER／QUERY 查無符合資料）→ 正常留白
- 語法錯誤、參照失效等會顯示 `#VALUE!`／`#REF!` → **看得見**

2026-08-18 就是因為用了 `IFERROR`，QUERY 的 `order by` 語法錯誤被吞掉，
`個案總表` 明明有 5 筆資料卻一片空白，看起來像「還沒有人回診」。

另外提醒：**`個案歷程` 空白是正常的**——它要黃色格子填了姓名與出生年才會出資料。
`個案總表` 才是「有資料就該自動出現」的那張，它空白就是有問題。

## 日期顯示格式統一為 `yyyy/mm/dd`（2026-08-19 加）

回應分頁的日期欄**從來沒設過格式**，會跟著試算表的地區設定走。這份試算表建立時
locale 是美國，於是：

| 位置 | 改之前 | 改之後 |
|---|---|---|
| `表單回應 1` 的 時間戳記 | `8/18/2026 13:03:33` | `2026/08/18 13:03:33` |
| `表單回應 1` 的 回診日期 | `9/4/2025` | `2025/09/04` |
| `個案歷程`／`個案總表` | `2025/08/07`（本來就對） | 不變 |

分析分頁本來就對，是因為 `buildHistorySheet`／`buildSummarySheet` 有
`setNumberFormat('yyyy/mm/dd')`；原始回應分頁沒人設過，才會露出美式排列。

**這是純顯示問題**：儲存格裡存的是日期序列值，數值本身沒錯，`個案總表` 的排序、
與前次差、累積減重 % 全都算對了。但門診當下人眼核對「3/4」是三月四日還是四月三日，
只能用猜的，故一律統一。

修法在 `applyDateFormats()`，兩層一起做：

1. `setSpreadsheetLocale('zh_TW')` ＋ `setSpreadsheetTimeZone('Asia/Taipei')`
   —— 根本解，之後**新增**的欄位預設就是 `yyyy/mm/dd`。
   （zh_TW 的公式參數分隔符仍是逗號，既有公式不受影響。）
2. 明確對時間戳記欄與回診日期欄 `setNumberFormat`
   —— locale 只改「預設」，**已經存在的欄位不會自動跟著變**，要另外設。

範圍設到 `getMaxRows()`（涵蓋尚未使用的空白列），表單新增回覆時會沿用該欄格式。

`buildAll()`／`repair()`／`reorderFields()`／`addVisitDateField()` 四支都會呼叫它，
所以任何一支跑完，格式都會是對的。

### 兩份回覆表要合併分析時

日後分析會把本表與**減重門診的 `*減重評估表 (回覆)`** 合併（2026-08-19 使用者指示）。
那份表的 locale 已是 zh_TW，日期排列本來就是年/月/日，但用 zh_TW 預設格式：

```
2025/9/25 下午 1:41:34      ← 月日不補零、中文 12 小時制
```

合併時的實際麻煩有二：匯出 CSV 後「下午 1:41:34」不是標準時間字串，程式要另寫剖析
規則；肉眼核對兩表時一邊補零一邊不補零，對齊要多想一秒。

故另備一支 **`alignAssessmentSheetDates()`**，把那份表的時間戳記也設成
`yyyy/mm/dd hh:mm:ss`。它**只改顯示格式**，不動資料、不建不刪分頁，
減重門診的月度統計不受影響。

**刻意不讓 `repair()` 連帶執行它**——不同檔案，分開跑才不會在修本工具時
意外動到門診那份正式運作中的資料。要在合併分析之前手動跑過一次。

> 順帶一提：合併分析時真正會出事的不是顯示格式，而是**型別**。兩份表的日期都是
> 日期序列值（不是文字），這點已確認；若哪天有人手動貼了文字日期進去，排序與比較
> 會靜默算錯，那才是要提防的。
